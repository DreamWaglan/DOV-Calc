# 回滚与恢复流程

回滚用于恢复最后一个经过验证的发布版本。回滚操作不得删除当前故障现场，也不得直接覆盖维护人员尚未保存的工作树。

## 回滚触发条件

出现下列任一情况时，应暂停当前发布并评估回滚：

- 首页、主要导航或搜索无法使用；
- 计算器、装备速查等核心工具发生阻断性错误；
- 大量深层链接返回 404；
- canonical、站点地图或基路径指向错误位置；
- 待授权正文、数据或素材进入公开构建；
- 线上产物与发布清单哈希不一致；
- 发布引入严重的移动端、可访问性或性能回归。

文字错误或单页非关键链接通常可以通过前向修复处理。涉及许可泄漏、核心功能不可用或范围广泛的路由错误时，应优先回滚。

## 选择恢复目标

恢复目标必须是最近一次同时满足下列条件的标签：

- 标签指向明确提交；
- 对应构建和内容报告全部通过；
- 线上检查结果已归档；
- 发布产物清单和 SHA256 可用；
- 没有已知的许可泄漏或关键故障。

如果没有符合条件的历史标签，应停止自动发布，并由维护人员选择已知可用提交。维护人员不得猜测恢复目标。

## 本地无损演练

```powershell
node scripts/release/verify-rollback.mjs
```

演练脚本在系统临时目录中完成以下操作：

1. 按发布清单校验当前 `dist`；
2. 创建完整归档副本；
3. 从归档副本恢复到另一个临时目录；
4. 对恢复后的每个文件重算 SHA256；
5. 比较文件数量、大小、单文件哈希和聚合哈希；
6. 删除临时目录，并把结果写入 `content/release/rollback-rehearsal.json`。

演练不切换分支、不修改提交，也不改写源文件或 `dist`。脚本只更新仓库内的演练报告。只有需要调查副本时，才可使用 `--keep-temp` 保留临时目录。

## 线上回滚步骤

1. 保存故障页面、工作流日志、当前提交和发布清单。
2. 确认最近一个已知可用标签及其提交。
3. 从该标签重新构建 GitHub Pages 产物，或重新发布已归档且哈希一致的产物。
4. 不在故障提交上临时拼接旧产物。
5. 等待 Pages 发布完成，再执行恢复后检查。

实际重新发布、移动标签或重写远端历史属于外部生产操作，必须由具备仓库权限的维护人员执行。标签一旦用于正式发布，不得移动到另一个提交；修复版本应使用新的语义化标签。

## 恢复后检查

- [ ] 首页和主要栏目可以打开；
- [ ] 计算器和装备速查完成一次基本操作；
- [ ] 至少三个深层链接可以直接访问；
- [ ] 故障路径不再返回意外 404；
- [ ] 404 页面仍可用；
- [ ] canonical 与 `sitemap.xml` 对应恢复版本；
- [ ] 线上关键文件与恢复版本清单哈希一致；
- [ ] GitHub Pages 显示的提交与恢复标签一致。

## 事件记录

事件记录应包含发现时间、影响范围、触发条件、故障提交、恢复标签、操作人、恢复时间、验证结果和后续修复项。若故障涉及来源许可，记录还应说明受影响页面、公开时间和清理结果。
